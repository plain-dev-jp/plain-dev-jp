## 組み込みLinux

※特定メーカーの構成の SoC については、現在も扱っているため詳細仕様は伏せています。

以下は、これらの SoC に一般的に見られる特徴を抽象化してまとめたものです。

- **省電力で高効率なマルチコア構成**  
  組み込み向けプロセッサに一般的な、低消費電力と十分な処理性能を両立した  
  CPUアーキテクチャを採用しており、ネットワーク処理や制御用途に適している。

- **ネットワーク処理のハードウェアアクセラレーション**  
  LAN/WAN のパケット転送やチェックサム計算、暗号化処理など、  
  一部のパケット処理を専用ハードウェアで高速化する仕組みを備えている。

- **Linux ベースのシステム構築が可能**  
  組み込み向け Linux と親和性が高く、ユーザー空間・ドライバ・起動処理の  
  カスタマイズが行いやすい。

### 共通の経験内容
- アプリケーション開発  
- 既存モジュールの改修・デバッグ

## 対応可能なデバッグ方法

アプリログ／カーネルログ、CPU使用率やメモリの監視、  
tcpdump／wireshark によるパケット解析など、外見の調査で原因が特定できない場合に、  
ソースコードレベルで踏み込んで調査する際の代表的なデバッグ手法を以下にまとめています。

- **ICE + IDE / GDB（Linux）によるデバッグ**  
  OSレス環境では ICE + IDE を用いたハードウェアレベルの解析が可能。  
  Linux環境ではリモート GDB によるユーザー空間のアプリケーション調査や、  
  仮想環境での IDE を用いたデバッグにも対応。

- **coredump デバッグ（Linux）**  
  モジュールが突然死した際に、スタックトレースやレジスタ・メモリ状態を解析し  
  異常終了の原因を特定するために使用。  
  ※coredump で直接的な死因は特定できるが、なぜその状況に至ったのか？については別途調査が必要になる場合が多い  

- **strace デバッグ（Linux）**  
  システムコールの流れを把握し、ソースコードと照合しながら  
  処理の進行状況や異常箇所を特定する際に使用。  
  ※処理の流れを把握する目的で使う場面が多く、直接的な原因特定に至るケースは少なめ

- **print文デバッグ（Linux）**  
  ほぼ原因が特定できており、挙動の証拠を取りたい場合に使用。  
  また、GDB ではタイミングがずれて再現しないようなデリケートなバグの調査時にも有効。  
  ※ただし print 文も思ったよりタイミングがずれるため、ログの量や出力位置には注意が必要

- **根性デバッグ（超巨大モジュールの深追い調査）**  
  担当外の巨大モジュールで、極めて低頻度（80万回に1回程度）で  
  どこかがメモリ破壊するような “気まぐれバグ” でも、  
  発生条件の洗い出しや事象発生時の解析を粘り強く繰り返し、  
  最終的に原因箇所まで到達する現場対応力があります。
