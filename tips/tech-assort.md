## スレッドセーフ（Thread-safe）

複数スレッドから同時アクセスしても状態が壊れないこと。  
組み込みや C 言語では特に注意が必要で、実務でも問題が起きやすい領域。

- ロックを取っていても「複数変数をまたぐ処理」は破綻しやすい  
  - 例：A と B を同時に更新する処理は、片方だけ更新される中途半端な状態が発生し得る

- C 言語のインクリメント／デクリメントは 1 行でもスレッドセーフではない  
  - `i++` は「読み取り → 加算 → 書き込み」の複数ステップで構成されるため、競合が起きる

- 標準ライブラリの中には非スレッドセーフな関数が存在する（意外と多い）  
  - `strtok`、`asctime`、`gmtime` などは内部で静的領域を使うため、同時呼び出しで壊れる

- 排他の仕方を誤るとデッドロックの危険性がある  
  - ロックの順番が統一されていないと、相互待ちが発生する  
  - ロックの粒度は「性能」と「安全性」のトレードオフになる

- スレッドセーフを満たすには「共有資源を減らす」「ロック範囲を明確にする」「状態をまたぐ処理を避ける」などの設計が重要

## シグナルセーフ（Signal-safe）

シグナルハンドラは任意のタイミングで割り込むため、ほぼすべての関数が危険。  
特に C 言語では「何が安全か」を正しく理解していないと、予期しない破壊が起きる。

- `malloc` / `free` / `printf` / `pthread_mutex_lock` などは絶対に使わない  
  - 内部でロックや静的領域を使うため、割り込みタイミングによって状態が壊れる

- 安全なのは `write` と `_exit` などの async-signal-safe 関数のみ  
  - POSIX が「シグナルハンドラ内で使ってよい」と保証している関数は非常に少ない

- シグナルセーフな関数は思ったよりも少ない  
  - `strlen` や `sprintf` なども安全ではない  
  - 「使ってよい関数リスト」を確認しないと簡単に破綻する

- シグナルハンドラ内では必要最低限の処理にとどめる  
  - フラグを立てる  
  - `write` でログを吐く  
  - `_exit` で終了する  
  この程度に抑えるのが実務的に安全

- 複雑な処理は絶対にハンドラ内で行わず、メインループ側で処理する設計が重要  
  - ハンドラは「通知」だけ  
  - 実際の処理は「通常のスレッド側」で行う

## COW（Copy-On-Write）string の危険性

COW 方式の `string` は、コピーしても内部バッファを共有するため、  
マルチスレッド環境では予期しない破壊が起きやすい。

- コピーしても内部バッファを共有するため、スレッド間で渡すとデータ競合が発生  
  - 片方が書き換えると、もう片方の string が勝手に変わる

- C++11 以降の `std::string` は非COWだが、古い環境では要注意  
  - 古い libstdc++ や一部組み込み向け実装では COW が残っている

- 一見「別スレッドにコピーする際に排他をかければ安全」に見えるが、実は危険  
  - コピー時点では安全でも、**その後の書き込みタイミングで共有バッファが破壊される**

- タイミングによっては、まだ存在しているはずの string が  
  「使い終わった」と判断されて再利用・メモリ解放されることがある  
  - その結果、ゴミを参照して誤動作  
  - あるいはメモリアクセス違反（SEGV）として表面化する

- COW string を安全に扱うには  
  - スレッド間で共有しない  
  - 書き込みを行わない  
  - COW を使わない実装に切り替える  
  などの対策が必要

## バグの調査・解析時の心得

バグ解析は「闇雲にコードを読む」よりも、まず状況を正しく把握することが重要。  
実務では、情報不足や誤った前提が原因で迷走することが多い。

### ● まずは現状把握（最重要）
- バグと言われると真っ先にソースコードを読みたくなるが、ぐっとこらえて“現状の事実”を整理する 
- 本来どう動くべきものが、現状どう動いているのかを整理する  
- 再現性はあるのか？ 再現方法は何か？  
- どの条件で発生し、どの条件では発生しないのか？  
- 「現状の事実」を正しく掴むことが最初の一歩

### ● 客からの申告は“そのまま鵜呑みにしない”
- 実務では、申告内容が事実と異なることが意外と多い  
  - 本質的な情報が抜けている  
  - 重要な前提が書かれていない  
  - 誤った理解で説明されている  
- 焦らず、腑に落ちるまで丁寧にヒアリングする  
  - 「本当にその操作をしたのか？」  
  - 「その状態で間違いなく再現するのか？」  
  - 「他の端末ではどうか？」  
- **事実と申告の差分を埋める作業が、バグ解析の半分を占める**

### ● 再現条件の特定が最強の武器
- 再現できれば、ほぼ解決したようなもの  
- 再現できない場合は「再現しない条件」を集める  
  - 時間帯  
  - ネットワーク状況  
  - 設定値  
  - 端末差  
- 再現条件の絞り込みは、原因の絞り込みに直結する

### ● 思い込みを捨てる
- 「このコードは絶対に正しいはず」  
- 「この処理は関係ないはず」  
- 「そんなこと起きるわけがない」  
こうした思い込みは、解析を長引かせる最大の原因

### ● 原因は1つとは限らない
- バグは複数の要因が重なって発生することがある  
- 1つの原因に固執すると、他の要因を見落とす  
- 複数の仮説を並行して持ち、事実で絞り込む姿勢が重要  
  （技術的にも心情的にも難しく、自分も毎回できていたとは言い切れないが、それでも必要なやり方）

### ● バグは“事実ベース”で追う
- ログ  
- 状態遷移  
- 通信内容  
- 実際の動作  
これらの「事実」を積み上げていくと、必ず原因に辿り着く。

## 文字列操作APIの思わぬ注意点（C言語）

C言語の文字列操作APIは「安全そうに見えて危険」なものが多い。  
特にバッファサイズぎりぎりで使うと、挙動が想像と異なり、簡単にバグやメモリ破壊につながる。

### ● snprintf
- バッファサイズぎりぎりまで使うと、**末尾に必ず NULL を書く**  
- そのため、出力が途中で切れる可能性がある  
- 「NULL 終端は保証されるが、内容は途中で切れる」という点を理解して使う必要がある

### ● strncpy
- バッファサイズぎりぎりまで使うと、**末尾に NULL を書かない**  
- つまり **NULL 終端されない文字列が出来上がる**  
- そのまま `strlen` や `printf` に渡すと暴走する  
- 「固定長コピー」用途なら安全だが、「文字列コピー」として使うと危険

### ● strncat
- 第3引数（size）は「追加する最大文字数」であり、  
  **NULL 終端のために +1 の領域が必要**  
- バッファサイズぎりぎりで使うと、**size+1 の位置に NULL を書きに行き、メモリ破壊が起きる**  
- `strncat(buf, src, sizeof(buf) - strlen(buf) - 1)` のように使う必要がある

### ● 共通する危険性
- どれも「安全そうな名前」だが、**使い方を誤ると簡単に SEGV やデータ破壊につながる**  
- 特に strncpy と strncat は「NULL 終端の扱い」が直感と異なるため、事故が多い
